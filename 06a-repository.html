6a. Repository und Entity Framework

Alltag: Eine Bibliothek hat einen Bibliothekar. Du sagst "Ich möchte Buch X", und er holt es. Wo und wie die Bücher im Lager stehen, musst du nicht wissen.
Merksatz: Das Repository ist der Bibliothekar für Daten. Der Rest des Codes fragt nur "gib mir Bestellung 5" und weiß nichts von SQL.

Wo wir stehen

Der BestellService ruft IBestellRepository auf. Wir haben das Interface bisher nur benutzt. Jetzt sehen wir, was dahintersteckt.

Controller
Service: Regeln und Ablauf
Repository: Daten holen und speichern
Datenbank

Erinnerung: Das Problem aus Seite 1

var db = new SqlConnection("Server=prod;...");
db.Open();
new SqlCommand($"INSERT INTO Bestellung VALUES ('{email}', {summe})", db)
    .ExecuteNonQuery();
  • SQL steht mitten in der Fachlogik.
  • Der String wird zusammengesetzt, das ist eine SQL-Injection-Lücke (jemand schreibt '; DROP TABLE ... in das E-Mail-Feld).
  • Man kann ohne echte Datenbank nichts testen.

Entity Framework in Kurzform

Entity Framework Core (EF Core) ist ein ORM ("Object-Relational Mapper"): Es übersetzt zwischen C#-Objekten und Datenbanktabellen. Statt SQL zu schreiben, arbeitet man mit Objekten.

// Entity: eine Zeile in der Tabelle Bestellungen
public class Bestellung
{
    public int Id { get; set; }
    public string Email { get; set; }
    public int Menge { get; set; }
    public decimal Summe { get; set; }
}

// DbContext: die Tür zur Datenbank
public class ShopDbContext : DbContext
{
    public ShopDbContext(DbContextOptions<ShopDbContext> options) : base(options) { }

    public DbSet<Bestellung> Bestellungen { get; set; }   // Tabelle
}

Das Repository

Interface (Vertrag, liegt bei der Fachlogik) 
public interface IBestellRepository
{
    Task<Bestellung?> HoleAsync(int id);
    Task<List<Bestellung>> HoleAlleAsync();
    Task HinzufuegenAsync(Bestellung b);
    Task SpeichernAsync();
}
Umsetzung (Technik, nutzt EF) 
public class BestellRepository : IBestellRepository
{
    private readonly ShopDbContext _db;

    public BestellRepository(ShopDbContext db)
        => _db = db;

    public Task<Bestellung?> HoleAsync(int id)
        => _db.Bestellungen.FindAsync(id).AsTask();

    public Task<List<Bestellung>> HoleAlleAsync()
        => _db.Bestellungen
               .AsNoTracking()
               .ToListAsync();

    public async Task HinzufuegenAsync(Bestellung b)
        => await _db.Bestellungen.AddAsync(b);

    public Task SpeichernAsync()
        => _db.SaveChangesAsync();
}

Der Service nutzt es

public async Task<Bestellung> AnlegenAsync(string email, int menge)
{
    var bestellung = new Bestellung { Email = email, Menge = menge };
    bestellung.Summe = _rabatt.Berechne(bestellung);

    await _repo.HinzufuegenAsync(bestellung);
    await _repo.SpeichernAsync();             // erst hier geht es in die Datenbank

    await _mail.SendeBestaetigungAsync(bestellung);
    return bestellung;
}

Kein SQL, keine Verbindung, keine Texte zum Zusammenbauen. Der Service sagt nur, was er braucht.

Wichtig: Änderungen merken und gemeinsam speichern

Add schreibt noch nicht in die Datenbank. Der DbContext merkt sich die Änderung. Erst SaveChangesAsync() schickt alles auf einmal, in einer Transaktion: entweder alles oder nichts.

Zusammenhang mit der Lebensdauer

Damit sich BestellService und RabattService dieselbe Verbindung teilen und gemeinsam speichern, muss der DbContext pro Anfrage genau einmal existieren: Scoped (siehe Lebensdauer). Das Repository greift auf ihn zu, also ist auch das Repository Scoped.

// Program.cs
builder.Services.AddDbContext<ShopDbContext>(o =>
    o.UseSqlServer(builder.Configuration.GetConnectionString("Shop")));   // Scoped

builder.Services.AddScoped<IBestellRepository, BestellRepository>();  // Scoped

Warum nicht gleich den DbContext im Service nutzen?

Diese Frage ist berechtigt. Der DbContext ist selbst schon eine Art Repository. Beide Wege sind verbreitet.

Mit eigenem RepositoryDirekt DbContext im Service
VorteilService kennt EF nicht, leicht gegen einen Fake auszutauschen, Abfragen an einer StelleWeniger Klassen, volle Möglichkeiten von EF
NachteilMehr Klassen, Gefahr, nur "durchzureichen"Service ist an EF gekoppelt, Tests brauchen eine In-Memory-Datenbank oder Test-DB
Passt wennFachlogik soll unabhängig von der Technik bleiben, viele Tests mit FakesKleine Anwendung, einfache Abfragen
Für unser Lernbeispiel nehmen wir das Repository, weil es DIP und Fakes aus den vorherigen Einheiten gut zeigt. Im echten Projekt entscheidet ihr im Team, was besser passt.

Gute Gewohnheiten

  • Immer parametrisieren: EF macht das automatisch. Wenn ihr doch mal rohes SQL braucht, nie Strings zusammensetzen, sondern Parameter nutzen.
  • Nur lesen? AsNoTracking() spart Speicher, weil EF Änderungen nicht verfolgen muss.
  • Alles async: Datenbankzugriffe warten. Mit await blockiert der Server dabei keinen Thread.
  • Repository gibt Entities zurück, keine DTOs. Die Umwandlung passiert am Rand im Controller (siehe DTOs).
  • Keine Geschäftsregeln im Repository. Es holt und speichert. Rabatt rechnet der Service.

Datenbank-Änderungen: Migrationen

Ändert man eine Entity (neue Spalte), muss sich auch die Datenbank ändern. EF erzeugt dafür Migrationen: kleine Skripte, die den Schema-Stand versionieren, ähnlich wie Git für den Code.

dotnet ef migrations add NeueSpalteMarge
dotnet ef database update
