6. Das Gesamtbild: Schichten

Wir haben Schritt für Schritt Verantwortungen getrennt. Zusammen ergibt das eine Schichtenarchitektur.

Die Schichten

Frontend (View)
React-Komponenten im Browser
Web-API (Controller)
ASP.NET-Controller, nimmt HTTP/JSON an
Anwendung / Fachlogik
Services (BestellService, RabattService)
Datenzugriff
Repositories (BestellRepository)
Extern
Datenbank, Mailserver, andere APIs

Regel: Aufrufe gehen nur von oben nach unten. Eine untere Schicht kennt die obere nicht. Die Controller kennen keine SQL-Details, die Datenbank kennt kein React.

Der DI-Container steht daneben und verdrahtet beim Start alle Teile miteinander. Zur Laufzeit ruft jeder nur seinen Nachbarn über ein Interface auf.

Leitfragen für den Alltag

  • Hat diese Klasse nur einen Grund, sich zu ändern?
  • Kann ich sie testen, ohne echte DB/Mail/Netzwerk?
  • Kennt sie nur Dinge, die in der Schicht unter ihr liegen?
  • Wüsste ein Neuer, wo er eine Änderung machen muss?
Wichtig: Architektur ist ein Werkzeug, kein Selbstzweck. Für ein 50-Zeilen-Skript braucht es keine vier Schichten. Der Aufwand lohnt sich, wenn der Code wächst, im Team entsteht und lange leben soll.

Wie geht es weiter?

  • Unit-Tests mit Mocks
  • Repository-Pattern, DTOs
  • DI-Lebensdauern (Singleton / Scoped / Transient)
  • SOLID, Clean/Hexagonal Architecture
