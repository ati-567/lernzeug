D: Dependency Inversion Principle

Von Interfaces abhängen, nicht von konkreten Klassen

Wichtigkeit: ★★★★★ Sehr wichtig (2. von 5 in der Lernreihenfolge)
Ohne DIP gibt es kein sauberes Dependency Injection und keine einfachen Unit-Tests. Es ist die Grundlage von Seite 4.
Alltag: Dein Laptop-Ladegerät hängt am USB-C-Standard, nicht an einer bestimmten Steckdosenmarke.
Regel: Wichtige Klassen (Fachlogik) sollen nicht von Details (SQL, SMTP) abhängen, sondern von Interfaces. Die Details richten sich nach dem Interface.

Beispiel

Verstößt 
class BestellService
{
    private SmtpMailService _mail = new SmtpMailService();
}
Die Fachlogik kennt das Detail (SMTP) und kann es nicht tauschen.
Passt 
class BestellService
{
    private readonly IMailService _mail;
    public BestellService(IMailService mail) => _mail = mail;
}
Der Service kennt nur den Vertrag. SMTP, Fake oder anderer Dienst sind austauschbar.
Nicht verwechseln: Dependency Inversion ist das Prinzip ("hänge von Interfaces ab"). Dependency Injection ist die Technik (Abhängigkeiten von außen übergeben), mit der man es umsetzt.

Woran erkenne ich es?

Steht in der Fachlogik ein new für eine Datenbank, Mail oder externe API? Dann fehlt DIP.
