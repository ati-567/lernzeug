4c. Unit-Tests mit Fakes und Mocks

Alltag: Ein Pilot übt im Flugsimulator. Er lernt alle Handgriffe, ohne dass echtes Kerosin verbrannt wird und ohne dass jemand in Gefahr ist. Ein Fake ist der Simulator für unseren Code.
Merksatz: Ein Unit-Test prüft eine Klasse allein. Ihre Abhängigkeiten ersetzt man durch Fakes, deshalb braucht man DI.

Warum testen?

Auf Seite 1 haben wir gefragt: "Wie teste ich den Rabatt, ohne dass eine echte Mail rausgeht?" Jetzt lässt sich das beantworten. Ein Test:

  • läuft in Millisekunden, ohne Datenbank, ohne Mailserver, ohne Netzwerk,
  • sagt sofort, ob eine Änderung etwas kaputt gemacht hat,
  • dokumentiert, wie die Klasse sich verhalten soll.

Der einfachste Fall: Klasse ohne Abhängigkeiten

Der RabattService braucht nichts von außen. Hier ist kein Fake nötig.

public class RabattServiceTests
{
    [Fact]
    public void Berechne_Menge_ueber_10_gibt_10_Prozent_Rabatt()
    {
        // Arrange
        var service = new RabattService();
        var bestellung = new Bestellung { Menge = 20, Preis = 10m };

        // Act
        var summe = service.Berechne(bestellung);

        // Assert
        Assert.Equal(180m, summe);     // 20 * 10 = 200, minus 10 %
    }

    [Fact]
    public void Berechne_Menge_bis_10_gibt_keinen_Rabatt()
    {
        var service = new RabattService();
        var bestellung = new Bestellung { Menge = 10, Preis = 10m };

        var summe = service.Berechne(bestellung);

        Assert.Equal(100m, summe);
    }
}

Der Name sagt, was passieren soll. Wenn ein Test rot wird, weiß man schon aus dem Namen, was kaputt ist. Das hier ist xUnit. NUnit und MSTest funktionieren ähnlich.

Der interessante Fall: Klasse mit Abhängigkeiten

Der BestellService braucht Mail und Datenbank. Beides wollen wir im Test nicht echt benutzen. Dank Konstruktor-Injection übergeben wir einfach Ersatz:

Ohne DI (Seite 3) 
public void Anlegen(Bestellung b)
{
    new MailService().Sende(b);
    new BestellRepository().Speichern(b);
}
Im Test geht echte Mail raus, und die echte Datenbank wird beschrieben. Ein Test ist unmöglich.
Mit DI (Seite 4) 
public BestellService(
    IMailService mail,
    IBestellRepository repo) { ... }
Im Test übergeben wir Fakes. Keine Seiteneffekte.

Fakes von Hand

Ein Fake ist eine kleine Klasse, die dasselbe Interface umsetzt und sich nur merkt, was passiert ist.

public class FakeMailService : IMailService
{
    public List<Bestellung> Gesendet = new();

    public void SendeBestaetigung(Bestellung b) => Gesendet.Add(b);
}

public class FakeBestellRepository : IBestellRepository
{
    public List<Bestellung> Gespeichert = new();

    public void Speichern(Bestellung b) => Gespeichert.Add(b);
}
[Fact]
public void Anlegen_speichert_und_sendet_Mail()
{
    // Arrange
    var mail = new FakeMailService();
    var repo = new FakeBestellRepository();
    var service = new BestellService(mail, repo, new RabattService());

    // Act
    service.Anlegen(new Bestellung { Email = "a@b.de", Menge = 20, Preis = 10m });

    // Assert
    Assert.Single(repo.Gespeichert);
    Assert.Equal(180m, repo.Gespeichert[0].Summe);
    Assert.Single(mail.Gesendet);
}

Der Test prüft, dass gespeichert, richtig gerechnet und eine Mail angestoßen wurde, ganz ohne echte Außenwelt.

Mocks mit einer Bibliothek

Für jede Abhängigkeit einen Fake zu schreiben wird mühsam. Bibliotheken wie Moq oder NSubstitute erzeugen Fakes im Test selbst.

[Fact]
public void Anlegen_sendet_genau_eine_Mail()
{
    // Arrange
    var mail = new Mock<IMailService>();
    var repo = new Mock<IBestellRepository>();
    var service = new BestellService(mail.Object, repo.Object, new RabattService());
    var bestellung = new Bestellung { Email = "a@b.de", Menge = 20, Preis = 10m };

    // Act
    service.Anlegen(bestellung);

    // Assert
    mail.Verify(m => m.SendeBestaetigung(bestellung), Times.Once);
    repo.Verify(r => r.Speichern(bestellung), Times.Once);
}

Verify prüft, ob eine Methode wie oft aufgerufen wurde.

Begriffe: Fake, Stub, Mock

BegriffGemeint istBeispiel
FakeEinfache Ersatz-Umsetzung mit echtem VerhaltenFakeBestellRepository mit einer Liste im Speicher
StubLiefert feste Antworten, damit der Test weiterläuftEin Repository, das immer "Bestellung #5" zurückgibt
MockPrüft, ob und wie etwas aufgerufen wurdeVerify(... Times.Once)
Praxis: Im Alltag sagt man oft "mocken" für alle drei. Wichtig ist der Gedanke: eine Abhängigkeit im Test durch Ersatz austauschen.

Was testet man, was nicht?

Gut testbar
  • Fachlogik in Services (Rabatt, Regeln)
  • Verzweigungen und Grenzfälle (Menge 10 / 11, Menge 0)
  • Fehlerfälle (ungültige Eingabe, nichts gefunden)
Meist nicht als Unit-Test
  • Getter und Setter
  • Das Framework selbst (Routing, JSON)
  • Echte Datenbank oder Mail (das sind Integrationstests)

Unit-Test und Integrationstest

Unit-TestIntegrationstest
Was wird geprüftEine Klasse alleinMehrere Teile zusammen, oft mit echter Test-Datenbank
AbhängigkeitenFakes oder MocksEcht oder Test-Variante
GeschwindigkeitMillisekundenSekunden
AnzahlVieleWenige, für die wichtigsten Abläufe

Was Tests über den Code verraten

  • Test ist schwer zu schreiben? Die Klasse hat zu viele Abhängigkeiten oder ruft new auf. Das ist ein Hinweis auf SRP- oder DIP-Probleme.
  • Fünf und mehr Fakes für einen Test? Die Klasse macht vermutlich zu viel.
  • Test bricht bei jeder kleinen Änderung? Er prüft Details der Umsetzung statt das Verhalten.
