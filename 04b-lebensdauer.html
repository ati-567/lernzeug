4b. Lebensdauer: Singleton, Scoped, Transient

Alltag: Im Büro gibt es eine Kaffeemaschine für alle (Singleton). Jeder Gast bekommt ein Tablett für seinen Besuch (Scoped). Jeder Kaffee kommt in einem neuen Einwegbecher (Transient).
Merksatz: Die Lebensdauer legt fest, wie lange ein Objekt lebt und wer es sich teilt. Im Zweifel nimmt man Scoped.

Die Frage dahinter

Auf Seite 4 hat der Container die Objekte erzeugt. Dabei stand überall AddScoped. Aber wie oft erzeugt er ein Objekt? Bei jeder Anfrage neu? Nur einmal für die ganze Anwendung? Genau das stellt man mit der Lebensdauer ein.

services.AddSingleton<IZeitProvider, ZeitProvider>();   // einmal für alles
services.AddScoped<IBestellService, BestellService>();   // einmal pro Anfrage
services.AddTransient<IRechnungsNummer, RechnungsNummer>(); // jedes Mal neu

Die drei Lebensdauern

Singleton
Ein Objekt für die gesamte Anwendung. Es entsteht beim ersten Gebrauch und lebt, bis die Anwendung beendet wird. Alle teilen es sich.
Scoped
Ein Objekt pro Scope. In ASP.NET ist das eine HTTP-Anfrage. Innerhalb der Anfrage teilen sich alle dasselbe Objekt, die nächste Anfrage bekommt ein neues.
Transient
Jedes Mal, wenn jemand das Objekt anfordert, wird ein neues erzeugt. Nichts wird geteilt.

Sichtbar gemacht: Wer bekommt welches Objekt?

Szenario: Anna und Ben schicken je eine Bestellung ab. Dafür braucht jede Anfrage zwei Klassen, den BestellService und den RabattService. Beide fordern dasselbe Objekt an (zum Beispiel den DbContext).

Jedes farbige Feld ist ein Objekt. Gleiche Farbe und gleicher Buchstabe heißen: dasselbe Objekt.

Singleton: eines für alle
Anfrage von Anna
BestellService → Objekt A
RabattService → Objekt A
Anfrage von Ben
BestellService → Objekt A
RabattService → Objekt A
Ergebnis: 1 Objekt. Anna und Ben teilen sich dasselbe Objekt A, auch über mehrere Anfragen hinweg.
Scoped: eines pro Anfrage
Anfrage von Anna
BestellService → Objekt A
RabattService → Objekt A
Anfrage von Ben
BestellService → Objekt B
RabattService → Objekt B
Ergebnis: 2 Objekte. Innerhalb einer Anfrage teilen sich beide Klassen ein Objekt. Anna und Ben bekommen jeweils ihr eigenes.
Transient: immer ein neues
Anfrage von Anna
BestellService → Objekt A
RabattService → Objekt B
Anfrage von Ben
BestellService → Objekt C
RabattService → Objekt D
Ergebnis: 4 Objekte. Jede Klasse bekommt bei jeder Anforderung ein frisches Objekt. Nichts wird geteilt, auch nicht innerhalb einer Anfrage.
Zum Merken: Singleton = 1 Objekt insgesamt. Scoped = 1 Objekt pro Anfrage. Transient = 1 Objekt pro Anforderung.

Warum ist das wichtig? Ein Beispiel

Der BestellService und der RabattService arbeiten in einer Anfrage mit derselben Datenbank-Verbindung (DbContext). So werden Änderungen zusammen gespeichert, und es gibt keine halbfertigen Bestellungen.

Anfrage
→
BestellService
RabattService
→ teilen →
1 DbContext
(Scoped)

Wäre der DbContext ein Singleton, würden alle gleichzeitigen Nutzer dieselbe Verbindung teilen. Das führt zu Fehlern und durcheinandergeratenen Daten.

Wann nehme ich was?

LebensdauerNimm es für …Typische Beispiele
SingletonDinge ohne Zustand pro Nutzer, die teuer zu erzeugen sind oder bewusst geteilt werden. Muss threadsicher sein.Konfiguration, Cache, Uhrzeit-Provider, Logger
ScopedAlles, was zu einer Anfrage gehört oder mit der Datenbank arbeitet. Das ist der Standard.DbContext, Repositories, die meisten Services (BestellService), aktueller Benutzer
TransientKleine, leichte Objekte ohne gemeinsamen Zustand, die jeder für sich braucht.Einfache Hilfsklassen, Rechner, Validatoren
Faustregel:
  • Unsicher? Scoped.
  • Greift auf die Datenbank zu? Scoped.
  • Teilt sich Daten über alle Nutzer hinweg (Cache, Konfiguration)? Singleton.
  • Soll jeder sein eigenes, frisches Exemplar? Transient.

Unser Beispiel mit passender Lebensdauer

// Program.cs
services.AddDbContext<ShopDbContext>(...);                           // Scoped (Standard von AddDbContext)
services.AddScoped<IBestellRepository, SqlBestellRepository>();      // Scoped: nutzt den DbContext
services.AddScoped<IBestellService, BestellService>();               // Scoped: gehört zur Anfrage
services.AddScoped<IRabattService, RabattService>();
services.AddScoped<IMailService, SmtpMailService>();
services.AddSingleton<IZeitProvider, SystemZeitProvider>();          // Singleton: zustandslos, überall gleich

Die größte Falle: Singleton darf Scoped nicht festhalten

Eine Regel: Ein Objekt darf nur von Objekten abhängen, die mindestens genauso lange leben wie es selbst.

Falsch 
// Singleton lebt ewig ...
services.AddSingleton<ReportService>();
// ... hält aber einen Scoped DbContext fest
class ReportService
{
    public ReportService(ShopDbContext db) { }
}
Der DbContext sollte nach der Anfrage sterben, bleibt aber am Leben, weil das Singleton ihn festhält. Man nennt das "Captive Dependency". Er ist veraltet, und mehrere Nutzer teilen ihn.
Richtig 
services.AddScoped<ReportService>();

class ReportService
{
    public ReportService(ShopDbContext db) { }
}
Ein langlebiges Objekt hängt nur von gleich langlebigen oder langlebigeren Objekten ab.
Wer …darf was nutzen?
Singletonnur Singleton
ScopedScoped, Singleton, Transient
Transientalles
Praktisch: Im Development-Modus prüft ASP.NET das und wirft beim Start eine Exception, wenn ein Singleton ein Scoped-Objekt anfordert. Diese Fehlermeldung nicht wegkonfigurieren, sie hilft.

Die zweite Falle: Zustand im Singleton

Ein Singleton wird von vielen Nutzern gleichzeitig verwendet. Merkt es sich etwas in einem Feld, sehen es alle.

Gefährlich 
// Singleton!
class WarenkorbService
{
    private List<Artikel> _artikel = new();
    public void Hinzufuegen(Artikel a)
        => _artikel.Add(a);
}
Alle Nutzer teilen sich einen Warenkorb.
Besser 
// Scoped (oder Daten in DB/Session)
class WarenkorbService
{
    public WarenkorbService(IWarenkorbRepository repo) { }
}
Der Zustand liegt pro Nutzer in der Datenbank.
