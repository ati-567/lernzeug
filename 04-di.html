4. Dependency Injection (DI)

Alltag: Ein Handwerker bekommt sein Werkzeug gestellt, statt es selbst zu schmieden.
Merksatz: Eine Klasse sagt, was sie braucht, aber baut es nicht selbst.

Problem aus Seite 3: Der BestellService erzeugt seine Abhängigkeiten selbst mit new. Er ist fest an konkrete Klassen gekoppelt.

Bild: Der Koch

Ohne DI
Der Koch baut sich seinen Herd selbst, bevor er kochen kann. Er kann nur mit diesem einen Herd arbeiten.
Mit DI
Der Koch bekommt einen Herd in die Küche gestellt. Ob Gas oder Induktion, ist ihm egal. Er will nur kochen.

Schritt 1: Von konkret zu abstrakt (Interface)

Der Service braucht nur etwas, das Mails senden kann. Wie, ist egal.

public interface IMailService
{
    void SendeBestaetigung(Bestellung b);
}

public class SmtpMailService : IMailService { ... }   // echte Mail
public class FakeMailService : IMailService { ... }   // für Tests

Schritt 2: Abhängigkeiten von außen übergeben

Vorher 
public class BestellService
{
    public void Anlegen(Bestellung b)
    {
        var mail = new SmtpMailService();
        mail.SendeBestaetigung(b);
    }
}
Nachher (Konstruktor-Injection) 
public class BestellService
{
    private readonly IMailService _mail;

    public BestellService(IMailService mail)
    {
        _mail = mail;
    }

    public void Anlegen(Bestellung b)
    {
        _mail.SendeBestaetigung(b);
    }
}
Vertiefung: Wie Interfaces in DI funktionieren, wann man sie braucht und wann nicht, erklärt die nächste Seite.

Der Service sagt nur was er braucht (IMailService). Er weiß nicht, welche Klasse es ist, und kümmert sich nicht ums Erzeugen.

Schritt 3: Wer erzeugt dann die Objekte?

Der DI-Container übernimmt das. Er wird einmal beim Start konfiguriert (die "Verdrahtung"):

// Program.cs / Startup
services.AddScoped<IMailService, SmtpMailService>();
services.AddScoped<IBestellRepository, SqlBestellRepository>();
services.AddScoped<BestellService>();
Was heißt AddScoped? Es legt fest, wie lange das Objekt lebt: hier eine Anfrage lang. Es gibt drei Varianten, die erklärt die nächste Seite.
Container
(Verdrahtung)
→ erzeugt →
BestellService
← bekommt ←
SmtpMailService
als IMailService

Der Controller fordert im Konstruktor einfach BestellService an und bekommt ihn fertig zusammengebaut.

Der große Gewinn: Testen

var fakeMail = new FakeMailService();
var service  = new BestellService(fakeMail, new FakeRepository());

service.Anlegen(new Bestellung { Menge = 20, Preis = 10 });

Assert.Equal(180, fakeMail.ZuletztGesendet.Summe);   // keine echte Mail, keine DB
Gewonnen:
  • Testbar ohne echte DB und ohne Mailserver.
  • Implementierungen austauschbar (SMTP → Mail-Dienst) an einer Stelle.
  • Abhängigkeiten sind im Konstruktor sichtbar.

Begriffe

BegriffBedeutung
DependencyEtwas, das eine Klasse zum Arbeiten braucht
InjectionEs wird von außen übergeben statt selbst erzeugt
InterfaceDer "Vertrag": was kann es, ohne zu sagen wie
ContainerBaut die Objekte zusammen (Verdrahtung)
Inversion of ControlNicht ich erzeuge meine Helfer, sie werden mir gegeben
Typische Stolperfallen: Für jede Klasse ein Interface anlegen (nur bei echtem Bedarf). new trotzdem im Service benutzen. Zu viele Parameter im Konstruktor (Zeichen, dass die Klasse zu viel macht).
