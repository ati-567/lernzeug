1. Problemstellung: Alles in einer Datei

Alltag: Eine Klasse, die alles kann, ist wie ein Restaurant, in dem eine Person kocht, serviert, kassiert und putzt. Bei zehn Gästen bricht es zusammen.
Merksatz: Code, der alles in einem Block macht, ist schwer zu ändern, zu testen und zu verstehen.

Aufgabe: Ein Kunde gibt eine Bestellung auf. Das System soll sie prüfen, speichern, Rabatt berechnen, eine Mail senden und eine Bestätigung anzeigen.

Der "schnelle" Ansatz

public class BestellungPage
{
    public void OnSubmit(string email, int menge, decimal preis)
    {
        // 1. Validieren
        if (!email.Contains("@") || menge <= 0)
        {
            Response.Write("<p>Ungültige Eingabe</p>");
            return;
        }

        // 2. Rabatt berechnen
        decimal summe = menge * preis;
        if (menge > 10) summe = summe * 0.9m;

        // 3. In die Datenbank schreiben
        var db = new SqlConnection("Server=prod;...");
        db.Open();
        new SqlCommand($"INSERT INTO Bestellung VALUES ('{email}', {summe})", db)
            .ExecuteNonQuery();

        // 4. Mail senden
        var smtp = new SmtpClient("mail.firma.de");
        smtp.Send("shop@firma.de", email, "Danke", "Summe: " + summe);

        // 5. Antwort als HTML
        Response.Write("<h1>Danke!</h1><p>Summe: " + summe + "</p>");
    }
}
Es funktioniert. Aber was passiert, wenn sich etwas ändert?

Eine Methode, fünf Verantwortlichkeiten

Validierung
Rabatt-Logik
Datenbank
E-Mail
HTML-Ausgabe

Alles hängt in einer Klasse und einer Methode.

Die Schmerzen

SymptomUrsache
Schwer zu testenLogik ist fest mit DB, Mail und Web verdrahtet
Änderungen sind riskantEine Änderung kann überall etwas kaputt machen
Code wird kopiertLogik kann nicht wiederverwendet werden
Schwer zu lesenZu viele Themen auf einmal
Teamarbeit haktAlle ändern dieselbe Datei
Fachbegriff: Separation of Concerns (Trennung der Zuständigkeiten). Jeder Teil des Codes soll genau einen Grund haben, sich zu ändern.
