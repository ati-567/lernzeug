O: Open/Closed Principle

Erweitern, ohne Bestehendes zu ändern

Wichtigkeit: ★★★☆☆ Mittel wichtig (3. von 5 in der Lernreihenfolge)
Nützlich, sobald Code wächst (neue Rabattarten, neue Zahlarten). Im Anfang übertreibt man es leicht: erst einfach schreiben, aufteilen, wenn der zweite oder dritte if-Zweig kommt.
Alltag: Eine Steckdosenleiste: Neue Geräte einstecken, ohne die Wand aufzustemmen.
Regel: Offen für Erweiterung, geschlossen für Änderung. Neues Verhalten kommt durch neuen Code, nicht durch Umbauen von altem, funktionierendem Code.

Beispiel

Verstößt 
decimal Rabatt(Bestellung b)
{
    if (b.Kunde == "Standard") ...
    else if (b.Kunde == "VIP") ...
    else if (b.Kunde == "Partner") ...
    // jeder neue Typ: hier ändern
}
Jeder neue Kundentyp ändert diese Methode und kann Altes kaputt machen.
Passt 
interface IRabattRegel
{
    decimal Berechne(Bestellung b);
}
class VipRabatt    : IRabattRegel { ... }
class MengenRabatt : IRabattRegel { ... }
// neuer Rabatt = neue Klasse
Neuer Rabatt = neue Klasse. Bestehende Regeln bleiben unberührt.

Woran erkenne ich es?

Müssen wir für jede Neuerung dieselbe Methode wieder aufmachen (lange if/else- oder switch-Ketten)?
