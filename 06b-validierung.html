6b. Validierung und Fehlerbehandlung

Alltag: Am Flughafen wird mehrfach geprüft: beim Check-in, bei der Sicherheitskontrolle, am Gate. Jede Stelle prüft etwas anderes, und auf die letzte kann man sich nicht verlassen, wenn die erste fehlt.
Merksatz: React prüft für den Komfort, das Backend prüft für die Sicherheit. Auf die Prüfung im Frontend darf sich das Backend nie verlassen.

Die Frage

Auf Seite 2 stand: Geschäftsregeln gehören nicht ins React-Frontend. Aber wo prüft man dann, und wie erfährt der Benutzer, was falsch war?

Wer prüft was?

1. React: Komfort. "Das ist keine E-Mail", sofort beim Tippen.
2. Controller / DTO: Form. Pflichtfelder, Länge, Format. Passiert vor der Fachlogik.
3. Service: Fachregeln. "Bestellmenge darf das Lager nicht übersteigen."
4. Datenbank: Letzte Absicherung. Pflichtspalten, Eindeutigkeit, Fremdschlüssel.
EbeneZweckDarf man darauf verzichten?
ReactSchnelles Feedback, weniger unnötige AnfragenJa, es ist nur Komfort
DTO / ControllerOffensichtlich kaputte Eingaben abweisenNein
ServiceRegeln der FachlichkeitNein
DatenbankLetzte Verteidigung gegen Fehler im CodeNein
Warum nicht nur React? Jeder kann die Anfrage am Frontend vorbei selbst schicken (Postman, curl, Browser-Konsole). Eine Prüfung im Browser ist wie ein Schild "Bitte nicht eintreten" ohne Tür.

Ebene 2: Form-Prüfung am DTO

Das Eingabe-DTO (siehe DTOs) bekommt Regeln als Attribute:

public class BestellungAnlegenDto
{
    [Required, EmailAddress]
    public string Email { get; set; }

    [Range(1, 1000)]
    public int Menge { get; set; }
}

Mit [ApiController] am Controller prüft ASP.NET das automatisch. Ist etwas falsch, wird der Controller gar nicht erst aufgerufen, und es kommt direkt ein 400 Bad Request zurück.

HTTP 400
{
  "title": "One or more validation errors occurred.",
  "errors": {
    "Email": [ "The Email field is not a valid e-mail address." ],
    "Menge": [ "The field Menge must be between 1 and 1000." ]
  }
}

Ebene 3: Fachregeln im Service

Manche Regeln brauchen Daten oder Zusammenhänge. "Genug Lagerbestand?" kann man nicht mit einem Attribut prüfen. Das gehört in den Service.

public async Task<Bestellung> AnlegenAsync(string email, int menge)
{
    var lager = await _lagerRepo.BestandAsync();
    if (menge > lager)
        throw new FachlicherFehler("Nicht genug auf Lager.");

    // ... Rabatt, speichern, Mail ...
}
Wichtig: Der Service weiß nichts von HTTP. Er wirft einen fachlichen Fehler. Die Übersetzung in einen Statuscode passiert weiter außen.

Fehler zentral behandeln

Vorher 
[HttpPost]
public IActionResult Anlegen(...)
{
    try { ... }
    catch (FachlicherFehler e)
    { return BadRequest(e.Message); }
    catch (NichtGefunden e)
    { return NotFound(); }
    catch (Exception e)
    { return StatusCode(500); }
}
In jedem Controller derselbe try/catch.
Nachher 
[HttpPost]
public async Task<IActionResult> Anlegen(
    BestellungAnlegenDto dto)
{
    var b = await _service.AnlegenAsync(
        dto.Email, dto.Menge);
    return Ok(b);
}
Der Controller bleibt schlank, die Fehler fängt eine zentrale Stelle.

Diese zentrale Stelle ist ein Exception-Handler (Middleware). Er läuft vor allen Controllern und übersetzt Fehler einmalig in HTTP-Antworten:

app.UseExceptionHandler(a => a.Run(async ctx =>
{
    var fehler = ctx.Features.Get<IExceptionHandlerFeature>()?.Error;

    (int status, string text) = fehler switch
    {
        FachlicherFehler f => (400, f.Message),
        NichtGefunden n    => (404, n.Message),
        _                  => (500, "Es ist ein Fehler aufgetreten.")
    };

    ctx.Response.StatusCode = status;
    await ctx.Response.WriteAsJsonAsync(new { title = text });
}));
Achtung: Bei 500 nie die echte Fehlermeldung oder den Stack-Trace an den Browser schicken. Das verrät Interna. Das Detail gehört ins Log, der Benutzer bekommt einen allgemeinen Text.

Und in React?

React liest den Statuscode und zeigt etwas Passendes an.

async function absenden(daten) {
  const res = await fetch("/api/bestellungen", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(daten),
  });

  if (res.ok) {
    setBestellung(await res.json());
    return;
  }

  if (res.status === 400) {
    const fehler = await res.json();
    setFehler(fehler.errors ?? { allgemein: [fehler.title] });   // Fehler an die Felder
  } else {
    setMeldung("Etwas ist schiefgelaufen. Bitte später erneut versuchen.");
  }
}
  • 400: Fehler bei den passenden Feldern anzeigen ("Menge muss zwischen 1 und 1000 liegen").
  • 401 / 403: Zur Anmeldung leiten oder "Keine Berechtigung" zeigen.
  • 404: "Nicht gefunden".
  • 500 / Netzwerkfehler: Freundliche allgemeine Meldung, ohne Details.
