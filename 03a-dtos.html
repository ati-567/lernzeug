3a. DTOs und Entities: Was schicke ich an React?

Alltag: Im Restaurant bekommt der Gast die Speisekarte, nicht das Rezeptbuch mit Einkaufspreisen und Gewinnmargen. Die Küche kennt alles, der Gast sieht nur, was für ihn gedacht ist.
Merksatz: Die Datenbank-Klasse (Entity) bleibt im Backend. Nach außen gehen eigene, schlanke Klassen (DTOs).

Das Problem

Bisher haben wir Bestellung an drei Stellen benutzt: als Eingabe vom Frontend, als Klasse für die Datenbank und als Antwort zurück an React. Das wirkt praktisch, ist aber gefährlich.

public class Bestellung
{
    public int Id { get; set; }
    public string Email { get; set; }
    public int Menge { get; set; }
    public decimal Summe { get; set; }
    public decimal Marge { get; set; }           // intern!
    public string InterneNotiz { get; set; }     // intern!
    public bool IstBezahlt { get; set; }         // darf nicht vom Kunden kommen!
}

[HttpPost]
public IActionResult Anlegen(Bestellung b) { ... return Ok(b); }

Was kann schiefgehen?

Zu viel nach außen
Mit return Ok(b) sieht jeder im Browser die Marge und die InterneNotiz. Ein Blick in die Netzwerk-Ansicht reicht.
Zu viel von außen
Wer das JSON selbst baut, kann "istBezahlt": true oder "summe": 0.01 mitschicken. Das Backend übernimmt es. Man nennt das Overposting.
Zu enge Kopplung
Ändert man eine Spalte in der Datenbank, ändert sich automatisch die API. Das React-Frontend bricht, obwohl niemand es angefasst hat.

Die Lösung: Eigene Klassen für außen

DTO heißt "Data Transfer Object": eine reine Datenklasse, nur zum Transport zwischen Frontend und Backend.

React
⇄ DTO ⇄
Controller
→
Service
⇄ Entity ⇄
Datenbank
Eingabe-DTO (nur, was der Kunde senden darf) 
public class BestellungAnlegenDto
{
    public string Email { get; set; }
    public int Menge { get; set; }
}
Ausgabe-DTO (nur, was React sehen darf) 
public class BestellungDto
{
    public int Id { get; set; }
    public string Email { get; set; }
    public int Menge { get; set; }
    public decimal Summe { get; set; }
}

Die Entity Bestellung bleibt wie sie war, mit Marge, InterneNotiz und IstBezahlt. Sie verlässt das Backend nie.

Der Controller übersetzt

[HttpPost]
public IActionResult Anlegen(BestellungAnlegenDto eingabe)
{
    Bestellung bestellung = _service.Anlegen(eingabe.Email, eingabe.Menge);

    var antwort = new BestellungDto
    {
        Id    = bestellung.Id,
        Email = bestellung.Email,
        Menge = bestellung.Menge,
        Summe = bestellung.Summe,
    };
    return Ok(antwort);
}

Die Summe berechnet der Server (im RabattService). Der Kunde kann sie nicht mehr vorgeben, weil sie im Eingabe-DTO gar nicht vorkommt.

Wer macht die Übersetzung?

VarianteWann
Von Hand im Controller oder in einer kleinen Methode ToDto()Für den Einstieg. Man sieht genau, was passiert.
Mapper-Klasse (BestellungMapper)Wenn dieselbe Übersetzung an mehreren Stellen gebraucht wird.
Bibliothek (z. B. AutoMapper, Mapperly)Bei vielen Klassen. Erst einsetzen, wenn die Handarbeit nervt.
Faustregel: Lieber ein paar Zeilen Mapping zu viel als eine versehentlich offengelegte Spalte.

Wozu das Ganze?

ProblemWie DTOs helfen
Interne Daten sichtbarAusgabe-DTO enthält nur Erlaubtes
Kunde schreibt Felder, die er nicht darfEingabe-DTO enthält nur Erlaubtes
Datenbankänderung bricht ReactAPI bleibt stabil, nur das Mapping wird angepasst
Verschiedene Sichten auf dieselben DatenEine Entity, mehrere DTOs (Liste, Detail, Anlegen)

Unterschied in einem Satz

EntityDTO
WofürAbbild einer DatenbanktabelleTransport zwischen Frontend und Backend
Lebt woBackend (Service, Repository)An der Grenze (Controller)
EnthältAlle Spalten, auch interneNur was der Aufrufer braucht
Ändert sich, wennsich die Datenbank ändertsich die Anforderung des Frontends ändert
Ehrlich gesagt: Bei einer ganz kleinen internen Anwendung ohne sensible Felder ist die Entity als JSON manchmal vertretbar. Sobald etwas Internes in der Klasse steckt oder Frontend und Datenbank sich unabhängig entwickeln sollen, lohnen sich DTOs.
Neues Problem: Der BestellService erzeugt seine Helfer noch immer mit new. Weiter mit Dependency Injection.
