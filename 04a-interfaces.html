4a. Interfaces in Dependency Injection

Alltag: Eine Steckdose ist ein Vertrag: "Hier kommt Strom raus, Stecker Typ F passt." Dem Föhn ist egal, ob der Strom aus Wind, Kohle oder Solar kommt. Er kennt nur die Steckdose.
Merksatz: Ein Interface beschreibt, was etwas kann, nicht wie. Der Container entscheidet, welche Klasse dahintersteckt.

Was ist ein Interface?

Ein Interface ist eine Liste von Methoden ohne Inhalt. Es enthält keinen Code, nur das Versprechen: "Wer mich implementiert, kann das."

public interface IMailService
{
    void SendeBestaetigung(Bestellung b);
}

Eine Klasse, die das Interface implementiert, muss alle Methoden liefern:

public class SmtpMailService : IMailService
{
    public void SendeBestaetigung(Bestellung b)
    {
        // hier steht das "Wie": SMTP-Server, Login, Text, ...
    }
}

Vertrag (das Was)
←
SmtpMailService

Warum braucht DI Interfaces?

DI heißt: Eine Klasse bekommt ihre Abhängigkeiten von außen. Aber was genau soll sie bekommen? Es gibt zwei Möglichkeiten:

Konkrete Klasse anfordern 
public BestellService(SmtpMailService mail)
Der Service ist an SMTP gebunden. Für Tests oder einen anderen Anbieter muss er umgebaut werden. Auch mit DI bleibt die Kopplung hoch.
Interface anfordern 
public BestellService(IMailService mail)
Der Service weiß nur: "Ich bekomme etwas, das Mails senden kann." Welche Klasse es ist, entscheidet jemand anderes.
Merke: DI funktioniert technisch auch ohne Interfaces. Den vollen Nutzen (austauschbar, testbar) bekommt man aber erst mit ihnen. Das ist das Prinzip DIP.

Wer entscheidet, welche Klasse dahintersteckt?

Das passiert an einer Stelle: bei der Registrierung beim Start der Anwendung.

// Program.cs
services.AddScoped<IMailService, SmtpMailService>();
//                  ^ Vertrag      ^ Umsetzung

Das liest sich: "Wenn jemand IMailService will, gib ihm einen SmtpMailService."

Der Gewinn: Umsetzung tauschen, ohne den Service anzufassen

Es gibt mehrere Klassen für denselben Vertrag. Der BestellService bleibt immer gleich.

KlasseWofürWo registriert
SmtpMailServiceEchte Mails über SMTPProduktion
SendGridMailServiceAnderer Anbieter, falls wir wechselnspäter
FakeMailServiceMerkt sich Mails, sendet nichtsUnit-Tests
KonsolenMailServiceSchreibt die Mail nur ins LogEntwicklung
if (builder.Environment.IsDevelopment())
    services.AddScoped<IMailService, KonsolenMailService>();   // lokal: keine echten Mails
else
    services.AddScoped<IMailService, SmtpMailService>();       // Produktion

Der Wechsel des Mailanbieters ist eine Zeile in Program.cs. BestellService, Controller und Tests bleiben unverändert.

Und im Test?

public class FakeMailService : IMailService
{
    public Bestellung ZuletztGesendet;

    public void SendeBestaetigung(Bestellung b)
        => ZuletztGesendet = b;
}

// Test
var fake    = new FakeMailService();
var service = new BestellService(fake);   // kein Container nötig, wir übergeben es selbst

service.Anlegen(bestellung);

Assert.NotNull(fake.ZuletztGesendet);     // Mail wurde "gesendet"

Der Test braucht keinen Container. Die Klasse nimmt ihr Interface im Konstruktor, also reicht es, im Test selbst eine Fake-Klasse zu übergeben. Statt eigener Fakes kann man auch Bibliotheken wie Moq oder NSubstitute nutzen, die solche Nachbauten erzeugen.

Wann braucht eine Klasse ein Interface, wann nicht?

Interface sinnvollMeist unnötig
Zugriff auf Außenwelt: Datenbank, Mail, Dateien, externe APIs, UhrzeitReine Datenklassen (Bestellung, DTOs, Models)
Es gibt (oder gab) mehrere UmsetzungenEinfache Hilfsklassen ohne Abhängigkeiten, die man direkt testen kann
Man will die Klasse in Tests durch einen Fake ersetzenKlassen mit genau einer Umsetzung, die nie getauscht oder ersetzt wird
Services, die der Controller aufruft (IBestellService)Das Framework selbst (Controller, Program)
Faustregel: Interface für alles, was langsam, unsicher oder außerhalb unseres Codes ist (DB, Netz, Mail, Zeit). Nicht reflexartig für jede Klasse. Ein IBestellungModel mit einer einzigen Umsetzung bringt nur Schreibarbeit.

Was gehört in ein gutes Interface?

Schlecht 
public interface IMailService
{
    void Sende(SmtpClient client,
               MailMessage msg);
    SmtpServer Server { get; }
}
Das Interface verrät das Detail (SMTP). Ein anderer Anbieter passt nicht dazu. Man nennt das ein "lecks Interface".
Gut 
public interface IMailService
{
    void SendeBestaetigung(Bestellung b);
}
Das Interface spricht in Begriffen der Fachlichkeit. Wie die Mail rausgeht, bleibt verborgen.
  • Klein halten: Nur das, was der Nutzer wirklich braucht (siehe ISP).
  • Fachlich benennen: SendeBestaetigung statt SmtpSend.
  • Namenskonvention in C#: Interfaces beginnen mit I (IMailService), die Umsetzung heißt nach dem Wie (SmtpMailService). Ein Name wie MailServiceImpl ist unüblich.

Wo liegt das Interface?

Das Interface gehört dorthin, wo es gebraucht wird, nicht zur Umsetzung. Der BestellService definiert, was er braucht (IMailService). Die Umsetzung (SmtpMailService) kommt in eine technische Schicht.

Fachlogik
BestellService, IMailService
Technik / Infrastruktur
SmtpMailService, SqlBestellRepository

So hängt die Technik von der Fachlogik ab und nicht umgekehrt. Das ist die "Inversion" in Dependency Inversion.

Mehrere Umsetzungen gleichzeitig

Manchmal sollen alle Umsetzungen genutzt werden, zum Beispiel Mail und SMS:

services.AddScoped<IBenachrichtigung, MailBenachrichtigung>();
services.AddScoped<IBenachrichtigung, SmsBenachrichtigung>();

public class BestellService
{
    private readonly IEnumerable<IBenachrichtigung> _kanaele;

    public BestellService(IEnumerable<IBenachrichtigung> kanaele)
        => _kanaele = kanaele;

    public void Anlegen(Bestellung b)
    {
        foreach (var kanal in _kanaele)
            kanal.Sende(b);
    }
}

Ein neuer Kanal ist nur eine neue Klasse plus eine Registrierung. Der BestellService bleibt unverändert. Das ist das Open/Closed-Prinzip in der Praxis.
