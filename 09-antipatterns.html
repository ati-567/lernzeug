9. Anti-Patterns erkennen

Alltag: Ein Arzt kennt typische Krankheitsbilder. Wer "Fieber, Husten, Gliederschmerzen" hört, denkt sofort an Grippe. Anti-Patterns sind die typischen Krankheitsbilder von Code. Wer sie kennt, erkennt sie früh.
Merksatz: Ein Anti-Pattern ist eine Lösung, die auf den ersten Blick praktisch aussieht, aber später Probleme macht. Man erkennt sie an festen Symptomen.

Die vier Kandidaten

Anti-PatternKurz gesagtVerletztHeilmittel
Fat ControllerController macht allesSRPServices
God ClassEine Klasse weiß und kann allesSRP, OCPAufteilen nach Verantwortung
Service LocatorAbhängigkeiten heimlich aus dem Container holenDIPKonstruktor-Injection
Anämisches ModelDaten ohne Verhalten, Logik überall verstreutKapselungRegeln in die Entity
Wichtig: Ein Anti-Pattern ist kein Verbot und kein Beweis für schlechten Code. Es ist ein Warnsignal: "Hier lohnt sich ein genauer Blick." Die Zahlen in den Checklisten sind Richtwerte, keine harten Grenzen.

1. Fat Controller

Alltag: Ein Kellner, der auch kocht, abrechnet und den Einkauf macht. Bei Betrieb bricht alles zusammen.

So sieht es aus

[HttpPost]
public IActionResult Anlegen(BestellungAnlegenDto dto)
{
    if (dto.Email == null || !dto.Email.Contains("@"))
        return BadRequest("Ungültig");

    var summe = dto.Menge * 10m;
    if (dto.Menge > 10) summe *= 0.9m;

    using var cmd = new SqlCommand("INSERT INTO ...", _connection);
    cmd.ExecuteNonQuery();

    var smtp = new SmtpClient("mail.firma.de");
    smtp.Send("shop@firma.de", dto.Email, "Danke", "Summe: " + summe);

    return Ok(summe);
}

Erkenne ich es so

  • Im Controller stehen if-Ketten mit Fachregeln (Rabatt, Lager, Preise).
  • Im Controller stehen SqlCommand, DbContext, SmtpClient oder new auf Technikklassen.
  • Die Methode ist länger als ein Bildschirm.
  • Der Controller hat viele using-Zeilen auf Technik (Datenbank, Mail, Dateien).
  • Dieselbe Logik soll von einer zweiten Stelle genutzt werden, und man kopiert sie.
  • Tests brauchen einen laufenden Webserver.

Warum schlecht

Fachlogik ist an HTTP gebunden, nicht wiederverwendbar und kaum testbar. Zwei Leute ändern dieselbe Datei.

Besser

[HttpPost]
public async Task<IActionResult> Anlegen(BestellungAnlegenDto dto)
{
    var b = await _service.AnlegenAsync(dto.Email, dto.Menge);
    return Ok(new BestellungDto { Id = b.Id, Summe = b.Summe });
}

Der Controller macht nur drei Dinge: annehmen, weiterreichen, antworten. Alles andere gehört in Services.

2. God Class

Alltag: Der Kollege, den man für alles fragen muss, weil nur er Bescheid weiß. Fällt er aus, steht alles still, und jeder Wunsch landet bei ihm.

So sieht es aus

public class KundenManager
{
    public void Anlegen(Kunde k) { ... }
    public void Speichern(Kunde k) { /* SQL */ }
    public decimal BerechneBonus(Kunde k) { ... }
    public void SendeNewsletter(Kunde k) { /* SMTP */ }
    public string ErzeugeRechnungPdf(Kunde k) { ... }
    public bool PruefeKreditwuerdigkeit(Kunde k) { ... }
    public void ExportiereNachExcel(List<Kunde> l) { ... }
    // ... 40 weitere Methoden
}

Erkenne ich es so

  • Der Name endet auf Manager, Helper, Utils, Handler, Processor oder Common, oder er sagt nichts ("Service" ohne Thema).
  • Die Klasse hat Hunderte oder Tausende Zeilen und sehr viele Methoden.
  • Man kann ihre Aufgabe nicht ohne "und" beschreiben.
  • Der Konstruktor hat viele Parameter (fünf oder mehr), oder die Klasse erzeugt vieles selbst.
  • Sie wird bei fast jedem Ticket geändert, und im Team gibt es ständig Merge-Konflikte darin.
  • Fast jede andere Klasse hängt von ihr ab.
  • Beim Testen muss man ein Dutzend Abhängigkeiten nachbauen.

Warum schlecht

Jede Änderung kann irgendwo etwas anderes kaputt machen. Niemand überblickt die Klasse, und sie wächst weiter, weil es der "bekannte Ort" ist.

Besser

Aufteilen nach Verantwortung, nicht nach Zeilenzahl. Jede neue Klasse bekommt einen Namen, der ihre Aufgabe sagt. Gehe schrittweise vor: erst eine Verantwortung herauslösen, Tests grün halten, dann die nächste.

3. Service Locator

Alltag: Ein Koch, der heimlich ins Lager geht und holt, was er braucht. Von außen sieht niemand, welche Zutaten das Gericht wirklich braucht, bis es plötzlich fehlt.

So sieht es aus

public class BestellService
{
    private readonly IServiceProvider _provider;

    public BestellService(IServiceProvider provider)
        => _provider = provider;

    public void Anlegen(Bestellung b)
    {
        var mail = _provider.GetRequiredService<IMailService>();   // heimlich geholt
        var repo = _provider.GetRequiredService<IBestellRepository>();

        repo.Speichern(b);
        mail.SendeBestaetigung(b);
    }
}

Das funktioniert und nutzt sogar den Container. Aber es ist keine echte Dependency Injection.

Erkenne ich es so

  • Im Konstruktor steht IServiceProvider, IContainer oder eine statische Klasse wie ServiceLocator.Get<T>().
  • Im Code stehen Aufrufe wie GetService<T>() oder GetRequiredService<T>() mitten in der Fachlogik.
  • Man sieht an der Klasse von außen nicht, was sie braucht.
  • Im Test fehlt eine Abhängigkeit und man erfährt es erst zur Laufzeit, mit einer Exception tief im Ablauf.
  • Für Tests muss man einen ganzen Container aufbauen, statt einfach Fakes zu übergeben.

Warum schlecht

Die Abhängigkeiten sind versteckt. Der Compiler hilft nicht, und fehlende Registrierungen fallen erst beim Ausführen auf. Das widerspricht dem Kern von DI: "Eine Klasse sagt, was sie braucht."

Besser

public class BestellService
{
    private readonly IMailService _mail;
    private readonly IBestellRepository _repo;

    public BestellService(IMailService mail, IBestellRepository repo)
    {
        _mail = mail;
        _repo = repo;
    }
}

Jetzt sieht man im Konstruktor sofort, was die Klasse braucht. Im Test genügen zwei Fakes.

Ausnahmen: An der Composition Root (Program.cs), in Middleware oder Fabriken, die zur Laufzeit entscheiden, welche Umsetzung gebraucht wird, ist der Zugriff auf den Container in Ordnung. In normaler Fachlogik nicht. Auch das Gegenteil, zu viele Konstruktor-Parameter, ist ein Warnsignal, aber kein Grund für einen Locator. Dann hat die Klasse zu viele Aufgaben (siehe God Class).

4. Anämisches Model

Alltag: Ein Auto, das nur aus Karosserie besteht. Alle Funktionen (Lenken, Bremsen) sitzen in der Werkstatt nebenan, und jeder Mechaniker macht es ein bisschen anders.

So sieht es aus

// Das Model: nur Felder, kein Verhalten
public class Bestellung
{
    public int Id { get; set; }
    public int Menge { get; set; }
    public decimal Summe { get; set; }
    public string Status { get; set; }
}

// Alle Regeln liegen verstreut in Services
public class BestellService
{
    public void Bezahlen(Bestellung b)
    {
        if (b.Status == "Storniert") throw new Exception("...");
        b.Status = "Bezahlt";
    }
}

public class RechnungService
{
    public void Erstellen(Bestellung b)
    {
        if (b.Status == "Storniert") return;   // dieselbe Regel, nochmal
        ...
    }
}

Erkenne ich es so

  • Die Entity besteht nur aus get; set;, ohne eine einzige Methode mit Fachlogik.
  • Alle Eigenschaften sind von überall änderbar (public set).
  • Dieselbe Regel (if (b.Status == "Storniert")) steht an mehreren Stellen in verschiedenen Services.
  • Services sind voller Code, der fremde Felder abfragt und ändert: b.Menge, b.Status, b.Summe.
  • Ein Objekt kann in einen ungültigen Zustand geraten (Menge = -5, Summe passt nicht zur Menge), und niemand schützt es.

Warum schlecht

Wenn sich eine Regel ändert, muss man alle Stellen kennen, die sie benutzen. Vergisst man eine, entstehen Fehler. Das Objekt kann sich selbst nicht gegen falsche Werte schützen.

Besser: Regeln in die Entity

public class Bestellung
{
    public int Id { get; private set; }
    public int Menge { get; private set; }
    public decimal Summe { get; private set; }
    public BestellStatus Status { get; private set; }

    public void Bezahlen()
    {
        if (Status == BestellStatus.Storniert)
            throw new FachlicherFehler("Stornierte Bestellung kann nicht bezahlt werden.");
        Status = BestellStatus.Bezahlt;
    }

    public void MengeAendern(int neueMenge)
    {
        if (neueMenge <= 0) throw new FachlicherFehler("Menge muss positiv sein.");
        Menge = neueMenge;
    }
}

Jetzt steht die Regel an einer Stelle, und die Bestellung kann nicht mehr in einen ungültigen Zustand geraten. Der Service sagt nur noch bestellung.Bezahlen().

Ehrlich gesagt: Unser Lernbeispiel ist selbst etwas anämisch. Bestellung ist eine reine Datenklasse, und der Rabatt steckt im Service. Das ist bei vielen .NET-Projekten üblich und für Einsteiger leichter zu verstehen. Es wird erst zum Problem, wenn dieselben Regeln mehrfach auftauchen oder Objekte ungültig werden können. Nicht jede Datenklasse braucht Methoden. Reine Transportklassen (DTOs) sollen sogar anämisch sein.

Schnell-Check: Was sehe ich, was ist es?

Ich sehe …Verdacht
SQL oder new SmtpClient im ControllerFat Controller
Eine Klasse "…Manager" mit 40 Methoden zu vielen ThemenGod Class
IServiceProvider im Konstruktor und GetRequiredService im CodeService Locator
Entity nur mit get; set; und dieselbe if-Regel in drei ServicesAnämisches Model
Konstruktor mit acht ParameternGod Class (Klasse macht zu viel)
Test braucht Webserver oder Datenbank für reine LogikFat Controller oder fehlende Interfaces

Wie gehe ich vor, wenn ich eins finde?

  1. Nicht sofort umbauen. Erst prüfen: Ist es wirklich ein Problem, oder ist die Klasse klein und stabil?
  2. Test schreiben, der das aktuelle Verhalten festhält, soweit es geht.
  3. Kleine Schritte: eine Verantwortung herauslösen, Tests laufen lassen, dann die nächste.
  4. Nur anfassen, was man sowieso ändert. Wer an einer Stelle arbeitet, räumt sie dabei auf (Pfadfinderregel: den Platz sauberer verlassen, als man ihn vorgefunden hat).
