8. Projektstruktur: Wohin gehört welche Klasse?

Alltag: In einem Haus gibt es Räume: Küche, Bad, Schlafzimmer. Niemand kocht im Bad. Ein Projekt braucht auch Räume, damit jeder weiß, wo er etwas findet und wo er etwas hinlegt.
Merksatz: Die Schichten aus Seite 6 werden zu eigenen Projekten in der Solution. So sorgt der Compiler dafür, dass niemand die Regeln bricht.

Die Frage

Wir haben Controller, Services, Interfaces, Repositories, Entities, DTOs und einen DI-Container. Auf Seite 6 haben wir Schichten gezeichnet. Aber wie sieht das in Visual Studio aus, und wohin kommt BestellService, wohin SmtpMailService?

Die Solution im Überblick

Eine Solution enthält mehrere Projekte (jedes wird zu einer eigenen DLL). Vier davon bilden den Kern:

Shop.sln
├── Shop.Domain            Kern: Entities, fachliche Regeln
├── Shop.Application       Anwendungslogik: Services, Interfaces
├── Shop.Infrastructure    Technik: Datenbank, Mail, externe APIs
├── Shop.Api               Eingang: Controller, DTOs, Program.cs
└── Shop.Tests             Unit-Tests
Domain
Die Fachlichkeit. Klassen wie Bestellung und fachliche Fehler. Kennt nichts anderes: kein EF, kein ASP.NET, keine Mail.
Application
Die Abläufe. BestellService, RabattService und die Interfaces, die sie brauchen (IBestellRepository, IMailService).
Infrastructure
Die Technik. ShopDbContext, BestellRepository, SmtpMailService. Setzt die Interfaces der Application um.
Api
Der Eingang. Controller, Eingabe- und Ausgabe-DTOs, Exception-Handler und Program.cs mit der Verdrahtung.

Wer darf wen kennen?

Das ist die wichtigste Regel: Abhängigkeiten zeigen nur nach innen, zur Domain hin.

Warum so? Das ist Dependency Inversion im großen Stil. Die Application sagt per Interface, was sie braucht (IMailService). Die Infrastructure liefert das Wie (SmtpMailService) und kennt dafür die Application. Würde die Application die Infrastructure kennen, wäre die Fachlogik wieder an SQL und SMTP gekettet.

Der Compiler passt auf

Ein Projektverweis ist eine echte Abhängigkeit. Versucht jemand, in der Application using Shop.Infrastructure; zu schreiben, ohne dass ein Verweis existiert, bekommt er einen Compilerfehler. Die Architekturregel wird durchgesetzt, ohne dass jemand im Code Review darauf achten muss.

<!-- Shop.Application.csproj -->
<ItemGroup>
  <ProjectReference Include="..\Shop.Domain\Shop.Domain.csproj" />
</ItemGroup>
<!-- kein Verweis auf Infrastructure oder Api -->

Hier ist nach Fachthema sortiert (alles zu "Bestellungen" zusammen), nicht nach Technik ("alle Services in einen Ordner"). Bei wachsender Anwendung findet man so alles zu einem Thema an einer Stelle.

Die Verdrahtung

Nur die Api kennt alle Projekte. Damit Program.cs nicht jede Klasse der Infrastructure einzeln aufzählt, bietet jedes Projekt eine kleine Methode an:

// Shop.Infrastructure/DependencyInjection.cs
public static class DependencyInjection
{
    public static IServiceCollection AddInfrastructure(
        this IServiceCollection services, IConfiguration config)
    {
        services.AddDbContext<ShopDbContext>(o =>
            o.UseSqlServer(config.GetConnectionString("Shop")));

        services.AddScoped<IBestellRepository, BestellRepository>();
        services.AddScoped<IMailService, SmtpMailService>();
        return services;
    }
}

// Shop.Api/Program.cs
builder.Services.AddApplication();                       // Services
builder.Services.AddInfrastructure(builder.Configuration); // DB, Mail

Diese eine Stelle in Program.cs nennt man die Composition Root: der einzige Ort, an dem Interfaces mit konkreten Klassen verbunden werden. Sonst steht nirgends im Code ein new SmtpMailService().

Was die Aufteilung bringt

WunschSo hilft die Struktur
Datenbank wechselnNur Infrastructure ändert sich, Application und Domain bleiben unverändert
Zweite Oberfläche (mobile App, Konsolentool)Neues Api-Projekt, das dieselbe Application nutzt
Fachlogik testenApplication-Tests ohne Datenbank und ohne Webserver
Zwei TeamsWeniger Konflikte, weil jeder in seinem Projekt arbeitet
Neue KollegenGleiche Struktur in jedem Projekt, man weiß, wo man suchen muss

Wann lohnt sich das, wann nicht?

Mehrere Projekte sinnvoll
  • Anwendung soll wachsen und lange leben
  • Mehrere Entwickler oder Teams
  • Echte Fachlogik, die unabhängig von Technik bleiben soll
  • Mehrere Schnittstellen (Web, Mobile, Batch)
Ein Projekt mit Ordnern reicht
  • Kleine interne Anwendung oder Prototyp
  • Hauptsächlich Daten anzeigen und speichern (CRUD)
  • Ein einzelner Entwickler
Praxis: Man kann klein starten. Ein Projekt mit den Ordnern Controllers, Services, Data, Domain, die dieselben Regeln einhalten, und später in eigene Projekte aufteilen, wenn es nötig wird. Die Regel "Abhängigkeiten zeigen nach innen" gilt auch dann.

Typische Fehler

FehlerFolge
DbContext oder EF-Attribute in der DomainDie Domain hängt an der Datenbanktechnik
Application verweist auf InfrastructureFachlogik kennt SQL und SMTP, Tests brauchen echte Technik
Controller enthält Fachlogik, die "nur kurz" dort stehtFat Controller (siehe Anti-Patterns)
Ein Projekt namens "Common" oder "Utils" für allesWird zur Müllhalde, jeder hängt an jedem
Für jede Kleinigkeit ein eigenes ProjektMehr Verwaltung als Nutzen
DTOs in der DomainDie Form der Schnittstelle bestimmt die Fachlichkeit

Namen für das Muster

Was wir hier gebaut haben, heißt je nach Buch Clean Architecture, Onion Architecture oder Hexagonale Architektur. Die Details unterscheiden sich, der Kern ist derselbe: Fachlogik innen, Technik außen, Abhängigkeiten zeigen nach innen. Es ist Dependency Inversion auf Projektebene.
